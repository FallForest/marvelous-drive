# Development

## Prerequisites

- Node.js **22.5+** (the server uses `node:sqlite`; developed on Node 26).
- Nothing else. No package install, no database server, no bundler.

## Run

```sh
node apps/server/src/index.js            # http://127.0.0.1:4400, data in ./data
PORT=4401 node apps/server/src/index.js  # another instance, same code
node --watch apps/server/src/index.js    # restart on change
```

The server serves the API and the web client from the same origin, so there is no
proxy and no CORS setup in development.

## Test

```sh
node --test apps/server/test/    # HTTP end-to-end: real SQLite, real sockets
node --test packages/cli/test/   # CLI: args, config, output, mock server
node --test apps/web/test/       # web logic: state, upload, motion helpers
```

```sh
npm run motion-lint              # static motion rules over apps/web/styles
npm run motion-check             # the above + a real-browser feel check
```

The feel check drives Chrome over the DevTools protocol, so it needs a running
server (`npm start`) and Chrome or Edge; CI runs only the static half. See
[UI-MOTION.md](UI-MOTION.md) for the layer model and the ten rules.

Server tests boot the real process through `apps/server/test/helpers.js` on an
ephemeral port with a throwaway `DRIVE_DATA_DIR`. Nothing is mocked that could be
real: SQLite is real, sockets are real, and the Office/PDF fixtures are built as
actual OOXML packages and PDF byte streams.

## Conventions

- ESM only, `node:` builtins only, no runtime dependency may be added without a
  very good reason.
- One route module per resource; `routes/` may import domain modules, never the
  other way round.
- All errors go through `HttpError` (`fail(status, code, message)`); never send a
  bare string.
- Anything touching more than one table runs inside `transaction()`.
- Blob refcounts change in the same function as the row that causes them.
- Names and ids: ids are generated by `randomId()`, names are normalised by
  `normalizeName()`.

## Releases and updates

A release is a tag, not a commit: `.github/workflows/release.yml` builds the
image, publishes it to GHCR and attaches `release/latest.json` to the release. A
deployment then moves forward from the account menu instead of a shell. The
cadence, the files a version bump touches, and the rollback procedure live in
[RELEASING.md](RELEASING.md).

Two shell scripts do the work and are validated by CI (`bash -n`, plus the
compose file itself):

| Script | Runs where | Does |
| --- | --- | --- |
| `scripts/deploy/update.sh` | updater container | back up, pin the manifest, pull, recreate, health-gate, roll back |
| `scripts/deploy/backup.sh` | updater container | consistent SQLite snapshot + tarball of the data volume |

The ordering inside `update.sh` is load-bearing: the snapshot of `.env` and the
compose files is taken **before** the new tag is pinned, so a failed health check
restores what was actually running. Test a change to that script by making the
health probe fail and checking that `backups/pre-update-<stamp>.env` comes back.

## Data directory

```
data/
  drive.db          SQLite database (WAL: drive.db-wal, drive.db-shm)
  .jwt-secret       32-byte hex secret, created on first boot
  blobs/ab/abcdef…  content-addressed files (sha256)
  tmp/              spool files, resumable chunks, zip scratch
```

Deleting `data/` resets the instance completely. Backups are a copy of that
directory while the server is stopped (or of `drive.db` plus a WAL checkpoint).

## Debugging

- `DRIVE_LOG=0` silences the request log; by default every non-asset request is
  logged with method, path, status and duration.
- `GET /healthz` proves the database is readable.
- Unhandled exceptions are logged with the request line and answered
  `500 INTERNAL_ERROR`; the stack never reaches the client.

## Adding an endpoint

1. Pick the resource module in `apps/server/src/routes/`.
2. Validate the body with plain checks or `ctx.json()`, throwing
   `ctx.fail(400, 'INVALID_INPUT', '…')`.
3. Put the reusable logic in the matching domain module: `nodes.js` or
   `versions.js` for tree and history, `storage/blobs.js` for bytes,
   `ops/search-index.js` for indexing. The directory decides the layer —
   `storage/` must not reach for HTTP, `text/` must not reach for the database.
4. Add a test in `apps/server/test/` that goes through HTTP, not through the
   module directly.
5. Document it in `docs/API.md` and add the route to `docs/CONTRACT.md` if it
   changes a shared shape.
